## "We have Kafka" doesn't get you orchestration

The single most useful source in the whole investigation was a Confluent field CTO — a *Kafka* person — conceding against interest that Kafka "lacks built-in tools for tracking workflow states or managing retries," and that building a full workflow engine on Kafka "adds significant custom development overhead." Kafka and a durable-execution engine are **complementary, not substitutes**.

"Durable state machine" is a phrase that hides a build list. To make one production-grade on raw Kafka, you own all of this yourself:

- **Durable timers and sleeps** — "wake this instance up in 14 days" needs a scheduler, a timer topic, and tombstoning.
- **Idempotency / exactly-once side effects** — at-least-once delivery means every consumer needs idempotency keys and a dedup store.
- **Saga compensation** — distributed rollback logic, orchestrated and tested by hand.
- **In-flight workflow versioning** — changing the state machine while thousands of instances are mid-flight. This is the hardest problem, and the one DIY teams discover last.
- **Poison messages, dead-lettering, backpressure, and a queryable "where is instance X" view.**

## XState (and its cousins) are not a shortcut

My colleague's suggestion was XState. It's an excellent state-*transition* library, but its own docs are explicit about the gaps: persistence is manual snapshot serialize/restore with **no storage backend**; on restore it does **not** re-run side effects (so exactly-once is your problem); and there's **no migration path** for versioning in-flight persisted state (a five-plus-year-old open issue). The Stately Inspector is a dev-time debugger, not a production console.

This is a whole *category*, not one tool. The same trap applies to Spring Statemachine (Java), Stateless (.NET), and the popular Python state machines — `transitions`, `python-statemachine`, `sismic`. They model beautifully and durably-execute nothing.

:::note If you want durable *Python* specifically

The answer is not a state-machine library — it's **DBOS**, **Temporal's Python SDK**, or **Hatchet**. Same idea for TypeScript: pair XState with a durable runtime like **Restate** (which has a first-class XState integration) rather than bolting persistence onto XState by hand.

:::

## "But I already run Conductor/Orkes"

This was the most personal thread for me, and the research changed my mind. Netflix **archived** the original Conductor OSS in December 2023 — the repo is read-only. It's now community-maintained with Orkes as commercial steward. The community edition is genuinely Apache-2, but every workflow is fundamentally a **JSON definition** (git-diffable and code-generable, so better than Camunda's BPMN, but still short of workflows-as-code).

The signal that landed hardest: **Netflix — which *created* Conductor — moved Spinnaker's Cloud-Operations orchestration onto Temporal** and cut transient deployment failures from ~4% to 0.0001%, without mentioning Conductor. When a tool's own author picks something else for hard reliability, that's data. And that same write-up confirms the migration ran as a **strangler-fig** — dynamic routing to either the legacy engine or Temporal, all apps onboarded within two quarters — so adopting an engine *beside* an incumbent, with Kafka as the seam, is a documented pattern, not a big-bang rewrite.

(Also of note for the DIY crowd: **Akka** relicensed to BSL, so the actor/event-sourcing escape hatch now needs a paid Lightbend license for production.)

## What changes if you add an event-sourcing database?

This was my favorite tangent, because it changes the DIY math more than anything else. Event sourcing persists state as an append-only log of events; current state is a fold over that log — which is *exactly* the model a durable-execution engine uses internally. Temporal's event history **is** event sourcing.

**What it buys you:** durable, replayable state (the missing "durable" in XState-alone); a complete audit trail and time-travel (the honest answer to the non-dev-visibility gap — build read-model dashboards over the log); rebuildable projections.

**What it still doesn't give you:** durable timers, retries, saga compensation, workflow versioning (and event *upcasting* is its own new versioning burden), human tasks, backpressure — plus eventual-consistency complexity you didn't have before.

One Kafka-specific note: Kafka is a *log*, not a great event *store* for aggregates (no per-entity streams, no optimistic concurrency). "Add an event-source DB" usually means a purpose-built store — EventStoreDB/Kurrent, Marten + Wolverine (.NET on Postgres), or Axon (JVM).

:::tip The punchline

Event store **+** a saga/process-manager framework = you are *assembling a durable-execution engine by hand*. A legitimate choice if you want to own it — but be clear that's what it is. And here's the shortcut hiding in the question: if you're adding a **Postgres** event store anyway, **DBOS** or Restate hand you the orchestration layer on that same database for free. So "add an event-source DB" doesn't weaken the engine case — for a Postgres shop, it quietly *strengthens* DBOS.

:::

## Bottom line

- Keep **Kafka** as the event backbone for everything.
- For **event pipelines and idempotent background jobs**, my hypothesis is right — stay on Kafka + idempotency keys + consumers. Don't adopt an engine.
- For **sagas and long-running human/timer/SLA workflows**, add a code-first durable-execution layer — **Temporal** if you want proven-at-scale and can wear the ops (or buy Cloud); **DBOS** or **Hatchet** if minimizing operational surface is the hard constraint and you'll pilot newer tech first.
- **Camunda is out** for me on three of four priorities (visual modeler, heavy ops, paid production). I never have to touch BPMN again.

All of it satisfies "no visual modeler," and every one of the code-first engines ships an ops UI that lets a non-developer inspect and retry — without adopting a BPMN designer.

## Caveats (what the evidence didn't nail)

Intellectual honesty, since this was AI-assisted:

- **DBOS production maturity is unverified.** License and architecture are confirmed; independent evidence of high-throughput, long-running production deployments is not. Its #1 ranking rests on a pilot proving out.
- **The concrete Kafka break-even thresholds are unverified.** My heuristic — choreographed saga + outbox + idempotency is fine up to a few steps, no compensation, no multi-day timers, no in-flight versioning; past that it flips — is reasoned, not sourced.
- **Trigger.dev and Hatchet are now verified** (Apache-2.0 and MIT respectively), but Trigger.dev's self-hosting footprint is heavy — Postgres + Redis + a container registry + object storage — and the vendor itself admits the Compose guide isn't production-ready.
- Several comparative framings came from vendor-adjacent blogs (corroborated by primary docs, but treat the *framing* with mild skepticism).
